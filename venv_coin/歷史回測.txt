歷史回測規劃

一、目標
使用 Binance USD-M Futures 的 15 分鐘 K 線，依固定版本的策略規則產生訊號，統計訊號出現後的價格變化，並評估計入手續費、滑價及適用時資金費率後的結果。

初期先回答：
- 訊號確認後一小時的收盤跌幅分布。
- 訊號確認後一小時內的最大有利跌幅，以及最大反向上漲幅度。
- 跌幅達到 1%、2% 等門檻的訊號比例。
- 不同商品、期間及市場狀態下的差異。

二、建議資料流程
1. 資料來源：使用 Binance 官方 REST API 下載歷史 K 線，使用 WebSocket 接收即時 K 線；不需要 Scrapy。Scrapy 主要用於爬取網站頁面，並非呼叫交易所 API 或接收 WebSocket 的首選工具。
2. 收集與保存：初期沿用目前的 JSONL 追加寫入流程，保留原始 K 線及策略判斷紀錄。
3. 分析：使用 DuckDB 直接查詢 JSONL；資料量增加或反覆分析變慢時，再批次轉為 Parquet，並由 DuckDB 查詢 Parquet。
4. 資料庫選項：若需要多個程式同時讀寫、索引查詢或集中管理，再評估 SQLite 或 PostgreSQL。MongoDB 也能使用，但不必只因為 JSONL 與 JSON 相似就採用它。

三、JSONL、MongoDB 與 Parquet
- JSONL 是文字檔格式，每行一筆 JSON。容易追加、檢視及搬移；DuckDB 可用 read_json_auto(..., format='newline_delimited') 直接查詢。副檔名是 .txt 不影響判斷，重點是檔案內容確實為 JSON Lines。
- MongoDB 的文件採 BSON 儲存，是類似 JSON 的二進位格式，並非直接把 JSONL 檔案當資料庫使用。可用 mongoexport 匯出 JSON 或 CSV，也可用 mongodump 備份。它提供索引及資料庫管理功能，但會增加服務維護成本。
- Parquet 是欄式二進位檔案格式，不是資料庫。它適合分析型讀取，通常能改善大量資料查詢速度並減少檔案大小；不適合直接用文字編輯器閱讀，也不需要每收到一根 K 線就單筆追加。
- 不必預先設定固定的轉檔筆數。先用 JSONL 實測，當查詢速度或檔案大小成為問題時，再批次轉 Parquet。

四、目前程式的資料行為與歷史資料缺口
- monitor.py 透過 REST 初始化及補漏，並監聽 15 分鐘 K 線 WebSocket；只在 Binance 事件標示 K 線已收盤（x=True）時處理，不會因每次未收盤更新都重寫檔案。
- strategy.py 將 K 線、策略評估及符合條件的訊號分別以 JSONL 追加到各自檔案。
- 目前沒有既存資料時，啟動初始化只下載最近 12 根已收盤 K 線；這足以暖機目前策略，但不足以代表完整歷史資料。正式回測前須新增或執行歷史 K 線下載流程，依 API 限制分頁下載所需期間，並檢查缺漏、重複及時間連續性。

五、一小時跌幅的回測定義
為避免使用訊號確認前尚不可成交的價格，建議先採用以下基準：
1. 訊號在第四根訊號 K 線收盤後確認。
2. 進場價使用訊號確認後下一根 15 分鐘 K 線的開盤價。
3. 一小時觀察區間為進場後的四根 15 分鐘 K 線。
4. 一小時後收盤跌幅： (進場價 - 一小時區間結束時的收盤價) / 進場價 * 100%。
5. 一小時內最大有利跌幅： (進場價 - 觀察區間最低價) / 進場價 * 100%。此數字是期間內最大有利波動，不代表一定能在最低價成交。
6. 一小時內最大反向上漲幅度： (觀察區間最高價 - 進場價) / 進場價 * 100%。
7. 另外以手續費、滑價及適用的資金費率計算淨結果；若只統計價格變化，須清楚標示為未扣成本的毛變化。

建議每筆回測結果至少保留商品、策略版本、訊號時間、進場時間與價格、一小時後收盤價、期間最低價與最高價、毛變化及成本後結果。統計平均值之外，也應觀察中位數、分位數、門檻達成率及最大不利波動。

六、回測注意事項
- 策略規則與資料期間要固定並記錄版本；不要只依單日結果調參。
- 避免前視偏誤：訊號只能在必要 K 線收盤後確認，成交價格使用之後可取得的價格。
- 明確處理缺漏 K 線、重複訊號、持倉重疊、停損／出場方式及交易成本。
- 回測前仍須固定突破確認、壓力區候選 K 棒選取、進場失效條件及出場規則；未定義前，結果只能視為探索性統計，不能直接當作可交易績效。
